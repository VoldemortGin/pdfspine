# pdfspine performance benchmark

Honest, reproducible comparison of **pdfspine** against three other PDF libraries — fitz/PyMuPDF (MuPDF C engine, AGPL, bench-only reference), pypdfium2 (PDFium C engine), and pypdf (pure Python) — on a shared public-domain corpus. Generated by `conformance/bench.py`.

## 2026-09-10: remaining render cost experiment (unreleased)

A small follow-up to the v0.8.0 render work removes a glyph-mask allocation/copy
and a repeated cache lookup, and replaces clip coverage division by an exactly
equivalent integer expression. The clip expression is exhaustively checked for
all 65,536 byte pairs. Glyph coverage, phase bins, colors and AA are unchanged.

On **35 available historical render documents**, page 0 at 150 dpi through the
real Python `Page.get_pixmap()` entry, the baseline at
`922355397a089d21d3cbee4937fdac9bd70bb0a6` and candidate measured:

| Metric | Baseline | Candidate |
|---|---:|---:|
| Corpus median of per-document medians | 12.0943 ms | 11.9573 ms |
| Relative to fitz on these same 35 documents | 2.436× | 2.408× |

The observed corpus change is **−1.13%**; 30/35 paired document medians are lower,
and the median of paired document ratios is 0.99097. All 35 output dimensions
and complete pixel buffers are byte-identical. The 8 missing historical assets
remain excluded, as listed in `gt/RENDER-REPORT.md`; no replacement PDFs were used.

**Measurement limits:** eight rounds used ABBA then BAAB order, with each
per-document result taking the median of 11 warm runs after one warmup. Each
operation opens the document, renders page 0, and closes it; interpreter startup
and output hashing are outside the timer. The four adjacent candidate/baseline
corpus ratios were **0.98484 / 1.00017 / 0.99888 / 0.98377**: two pairs were
essentially flat. Baseline round medians ranged 12.0778–12.1230 ms and candidate
round medians 11.8948–12.1140 ms. This is a small observed improvement with
variation, not evidence of a general or significant speedup. PRD §0 item 3's
major glyph/JPEG 2000 costs remain unresolved.

Both engines used independent Python environments on the same M4 Max, Python
3.12.11; fitz/PyMuPDF was 1.28.2, with median 4.9649 ms on this particular set.
Parallel workers deferred compilation and heavy evaluations during timing;
ordinary desktop processes remained running. Absolute times and the fitz ratio
are **not comparable to the older 27-document benchmark below**.

A 10-second native stack sample of the public Python render loop attributed
about 19.5% to first glyph mask rasterization, 11.4% to JPEG 2000 decoding, 8.9%
to clip intersection, and 6.1% to canvas conversion. These are sampled inclusive
costs from a repeated 35-page loop, not per-document medians. No decoder upgrade
or AA approximation was made. A separate fixed-stride RGB conversion experiment
had paired median ratio 1.000006 and was rejected.

Reproduction evidence is outside git in
`/Volumes/ExternalSSD/tmp/pdfspine-render-performance/`: `manifest.json` records
all 35 input paths/SHA-256 values and page/DPI parameters; `bench_worker.py`
executes the public API; `combined-rounds.json`, `combined-*-*.json` and
`combined-summary.json` retain every timing and output hash. `methodology.json`
records the baseline extension hash; `baseline-sample.txt` retains the profiler
stacks. Input locations and local interpreter paths must be adapted elsewhere.

## Summary

- **open** — vs fitz: pdfspine 1.26x faster; vs pypdfium2: pdfspine 1.65x faster; vs pypdf: pdfspine 18.29x faster.
- **text extraction** — vs fitz: pdfspine 2.26x faster; vs pypdfium2: pdfspine 1.22x slower; vs pypdf: pdfspine 6.90x faster.

## Methodology

- **Warm medians.** Each (library, document, operation) is run once to warm OS/file caches and validate the op, then timed 7 times; the reported per-document number is the median of those timed runs.
- **Subprocess isolation.** Every measurement runs in a fresh worker process via the correct interpreter — pdfspine in the project `.venv`, pypdf/pypdfium2 in a separate gitignored `.venv-bench`, fitz/PyMuPDF in the gitignored `.venv-oracle`. This keeps the AGPL/3rd-party deps out of our build's interpreter and contains crashes/hangs (a per-document wall-clock timeout marks a cell failed).
- **Operations.** `open` = open + read `page_count`; `text` = extract text over the *whole* document (pdfspine `page.get_text()`, pypdf `page.extract_text()`, pypdfium2 `textpage.get_text_bounded()`, fitz `page.get_text()`); `render` = rasterize page 1 at 150 dpi (pdfspine `page.get_pixmap(dpi=150)`, pypdfium2 `page.render(scale=150/72)`, fitz `page.get_pixmap(dpi=150)`).
- **Process-creation overhead** is excluded: workers are spawned once per (library, document) and time only the in-process op loop, never the interpreter startup.

## Caveats (read these)

- **Apples to different things.** pypdf is **pure Python** (no native code, no rasterizer); pypdfium2 wraps **PDFium**, the mature C/C++ engine from Chromium. pdfspine is **pure Rust**. A pure-Rust library beating a hand-tuned C engine is not the expectation — where pypdfium2 wins, that is the C engine's maturity showing.
- **fitz / PyMuPDF is AGPL-licensed and bench-only.** It wraps MuPDF (another mature C engine) and is used here purely as an external speed and differential reference. It is never imported into or linked with the Apache-2.0 build; it runs isolated in `.venv-oracle` and only its timings are recorded — no output is committed.
- **pdfspine's rasterizer is young.** The `render` path is a from-scratch Rust rasterizer; treat its render numbers as a snapshot of an evolving component, not a final state.
- **Text extraction is not normalized for accuracy here.** This harness measures *speed*, not output quality. Extraction accuracy vs the fitz oracle is tracked separately in `conformance/REPORT.md`.
- **Single machine, single run.** Numbers are from one Apple-silicon laptop and will differ on other hardware; re-run `bench.py` to reproduce locally.
